Tema 03

Infraestructura como código y CI/CD en Azure

Cómo pasar de crear recursos a golpe de clic en el Azure Portal a describirlos en un archivo que se puede ejecutar en cualquier cuenta. Bicep para describir la infraestructura, Azure Container Apps para correr el contenedor, y GitHub Actions con autenticación federada (OIDC) para desplegar automáticamente sin guardar ni una sola contraseña. Todo este tema documenta un despliegue real: el backend ms-tercero, para la Universidad El Bosque.

SECCIÓN 1Qué es Infraestructura como Código

Antes de este tema, crear la infraestructura de ms-tercero en Azure habría significado entrar al Portal, hacer clic en "Crear recurso", rellenar formularios para el registro de contenedores, para el entorno de Container Apps, para la Container App… siete u ocho pantallas, en un orden concreto, con nombres que hay que teclear igual en cada pantalla. Eso es infraestructura manual: funciona, pero vive solo en la memoria de quien hizo los clics.

Infraestructura como Código (IaC) es escribir esa misma infraestructura en un archivo de texto que una herramienta puede leer y ejecutar. El archivo describe el resultado final ("quiero un registro de contenedores llamado acrmstercero, en la región westus2, con SKU Basic"), no los pasos para llegar ahí. Eso se llama ser declarativo, en contraste con un script imperativo que diría "ejecuta este comando, luego este otro, luego este".

Analogía

Una receta de cocina imperativa dice "pon la olla al fuego, espera 5 minutos, añade la sal". Una receta declarativa diría simplemente "quiero una sopa con 2 % de sal, caliente". A la herramienta (el horno, en este caso Azure) le da igual el orden exacto de tus gestos: lo que te garantiza es el resultado final descrito.

La propiedad más importante de un buen archivo de IaC es la idempotencia: ejecutarlo dos veces seguidas no debe romper nada ni duplicar recursos. Si el recurso ya existe tal y como lo describiste, Azure no hace nada; si falta algo, lo crea; si algo cambió, lo actualiza. Por eso en este proyecto se pudo volver a ejecutar el mismo despliegue varias veces mientras se corregían los tres errores de la sección 6, sin tener que destruir nada a mano entre un intento y el siguiente.

Idea clave

IaC no es "un script que crea cosas". Es una descripción del estado final que se puede volver a aplicar cuantas veces haga falta, y que se puede llevar, intacta, a otra cuenta de Azure. Esa portabilidad fue la razón concreta por la que se eligió IaC para ms-tercero: la necesidad de poder replicar esta misma infraestructura en otra cuenta de Azure.

Autoevaluación
  1. ¿Qué diferencia hay entre un script imperativo y un archivo declarativo de IaC?
    El imperativo lista pasos a ejecutar en orden; el declarativo describe el resultado final que se quiere, y la herramienta decide cómo llegar ahí.
  2. ¿Por qué importa que un despliegue de IaC sea idempotente?
    Porque permite volver a ejecutarlo tras corregir un error, sin tener que borrar a mano lo que ya se había creado correctamente.

SECCIÓN 2Bicep: qué es y cómo se relaciona con ARM

Azure lleva años aceptando descripciones declarativas de infraestructura en un formato llamado ARM template (Azure Resource Manager template): un archivo JSON, válido, pero verboso y difícil de leer a simple vista. Bicep es un lenguaje más simple que se escribe a mano y que, por debajo, se compila a ese mismo JSON de ARM. Azure nunca "entiende" Bicep directamente: entiende ARM, y Bicep es la capa cómoda encima.

// Esto, en Bicep...
resource acr 'Microsoft.ContainerRegistry/registries@2023-07-01' = {
  name: acrName
  location: location
  sku: { name: 'Basic' }
}

...se traduce, al compilar, a decenas de líneas de JSON equivalente con la misma información. El comando para comprobar esa traducción sin desplegar nada es az bicep build: compila el archivo a un .json local y avisa de errores de sintaxis antes de gastar ni un segundo hablando con Azure.

Ejemplo real

En ms-tercero el archivo infra/main.bicep se validó así antes de cada intento de despliegue: az bicep build --file main.bicep. Encontrar un error de sintaxis en ese paso tarda segundos; encontrarlo después, a mitad de un despliegue real, puede tardar varios minutos (el tiempo que Azure tarda en crear los recursos anteriores antes de llegar al que falla).

Ojo con esto

Un archivo .bicep no se "ejecuta" como un script: se despliega con az deployment ... create (apéndice A). La diferencia no es solo de vocabulario: un despliegue de Bicep calcula primero qué cambió respecto al estado actual de Azure, y solo toca eso.

Autoevaluación
  1. ¿Bicep reemplaza a ARM o se apoya en él?
    Se apoya en él: Bicep se compila a un ARM template en JSON; Azure solo procesa ese JSON.
  2. ¿Para qué sirve az bicep build si de todas formas hay que desplegar con otro comando?
    Para detectar errores de sintaxis en segundos, de forma local, sin esperar a que el despliegue real llegue al recurso con el error.

SECCIÓN 3Scopes en Bicep: suscripción vs resource group

Todo recurso de Azure vive dentro de un resource group: una carpeta lógica que agrupa recursos relacionados para administrarlos (y borrarlos) juntos. Pero el propio resource group tiene que crearse en algún lado: un nivel por encima, en la suscripción.

Analogía

La suscripción es el edificio completo; un resource group es un piso del edificio; los recursos (el registro de contenedores, la Container App…) son las oficinas dentro de ese piso. No puedes pedir "crea la oficina 301" sin que exista primero el piso 3.

Un archivo Bicep declara su scope (ámbito) al principio con targetScope. En ms-tercero se usaron dos archivos con dos scopes distintos, en capas:

// infra/main.bicep -- vive al nivel de la SUSCRIPCIÓN
targetScope = 'subscription'

resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: resourceGroupName
  location: location
}

// delega todo lo de dentro del resource group a otro archivo
module appResources 'modules/app-resources.bicep' = {
  name: 'ms-tercero-app-resources'
  scope: rg
  params: { location: location, acrName: acrName, /* ... */ }
}

El archivo modules/app-resources.bicep, en cambio, no declara targetScope: por defecto su scope es resourceGroup, y recibe ese resource group desde afuera (scope: rg, arriba). Dentro de él viven el registro de contenedores, el espacio de Log Analytics, el entorno de Container Apps y la Container App (sección 4).

Idea clave

Separar en dos archivos por scope no es estético: es lo que permite que un solo comando, apuntando a main.bicep, cree el resource group y todo lo que va dentro, en cualquier suscripción nueva, sin pasos manuales intermedios.

Autoevaluación
  1. ¿Por qué main.bicep necesita targetScope = 'subscription' y el módulo no?
    Porque crear el propio resource group es una operación de nivel suscripción; todo lo que va adentro (el módulo) ya opera dentro de ese resource group, que es su scope por defecto.

SECCIÓN 4Los recursos reales: ACR, Log Analytics, entorno y Container App

El módulo app-resources.bicep declara cuatro recursos, en este orden de dependencia:

RecursoTipo ARMPara qué sirve
Azure Container Registry (acrmstercero)Microsoft.ContainerRegistry/registriesGuarda la imagen Docker del backend, versionada por etiqueta (ej. el SHA del commit).
Log Analytics workspaceMicrosoft.OperationalInsights/workspacesRecibe los logs de la aplicación. Container Apps lo exige: no hay entorno sin un destino para los logs.
Container Apps Environment (cae-ms-tercero)Microsoft.App/managedEnvironmentsLa "red" compartida donde corren una o varias Container Apps; aquí vive la configuración de logs.
Container App (ms-tercero-api)Microsoft.App/containerAppsEl propio contenedor en ejecución: imagen, variables de entorno, puerto expuesto, reglas de escalado.
Analogía

Azure Container Apps es un contenedor "sin servidor": igual que una función serverless, puede escalar a cero instancias cuando nadie lo usa (no cobra nada mientras duerme) y levantarse de nuevo cuando llega una petición. Es el punto medio entre "subir un jar a una máquina virtual que corre siempre" y "un clúster de Kubernetes completo" como AKS.

resource containerApp 'Microsoft.App/containerApps@2024-03-01' = {
  name: containerAppName
  identity: { type: 'SystemAssigned' }
  properties: {
    managedEnvironmentId: containerAppsEnv.id
    configuration: {
      ingress: { external: true, targetPort: 8080, transport: 'auto' }
    }
    template: {
      containers: [{
        name: 'ms-tercero'
        image: containerImage
        resources: { cpu: json('0.5'), memory: '1.0Gi' }
        env: [
          { name: 'AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT', value: azureDocumentIntelligenceEndpoint }
          // ...el resto de variables de configuración
        ]
      }]
      scale: { minReplicas: 0, maxReplicas: 1 }
    }
  }
}
Ejemplo real

Esas variables de entorno (AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT, etc.) llegan a la aplicación Spring Boot sin que exista ningún application.yml dentro de la imagen. Spring Boot tiene un mecanismo llamado relaxed binding: una variable de entorno en mayúsculas con guiones bajos, como AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT, se mapea automáticamente a la propiedad azure.document-intelligence.endpoint. Es la pieza que conecta el Bicep (que define variables de entorno) con el código Java (que define propiedades de configuración), sin que ningún secreto quede escrito en un archivo dentro del repositorio ni de la imagen.

El identity: { type: 'SystemAssigned' } de la Container App crea una identidad administrada: una cuenta de servicio que Azure gestiona automáticamente (sin contraseña que rotar) y a la que se le pueden asignar permisos sobre otros recursos. En este proyecto se intentó usarla para autenticarse contra el registro de contenedores — y ahí apareció el tercer error real de la sección 6.

Autoevaluación
  1. ¿Por qué Container Apps exige un Log Analytics workspace aunque no se vaya a mirar nunca?
    Porque el entorno (managedEnvironment) necesita un destino configurado para los logs de la aplicación; es un requisito estructural del recurso, no una opción.
  2. ¿Qué significa que la Container App pueda escalar a cero instancias?
    Que cuando no hay peticiones, Azure apaga el contenedor por completo (y no se cobra por cómputo) hasta que llegue la siguiente petición.

SECCIÓN 5Secretos: @secure() y por qué la clave nunca toca el repo

La clave de la API de Azure Document Intelligence es un secreto real: con ella, cualquiera puede consumir la cuota del recurso. Un archivo de IaC que la tuviera escrita en texto plano, subido a GitHub, sería equivalente a pegarla en un chat — y de hecho eso fue justo lo que pasó más de una vez durante el desarrollo de este proyecto, antes de automatizarlo (una de las razones por las que conviene rotar esa clave después).

Bicep resuelve esto con el decorador @secure(): marca un parámetro como sensible, de forma que Azure nunca lo registra en los logs de despliegue ni lo expone en el historial de az deployment.

// infra/main.bicep
@secure()
@description('API key del recurso de Azure AI Document Intelligence. Nunca se guarda en un archivo del repo: se pasa en el momento del despliegue.')
param azureDocumentIntelligenceKey string

Ese parámetro no vive en ningún archivo de parámetros versionado. El archivo que sí va al repositorio (infra/main.parameters.example.json) contiene solo los valores que no son secretos (nombres, región, ids de modelo); el archivo real con la clave (infra/main.parameters.json) está en .gitignore y se rellena solo en la máquina de quien despliega.

Ojo con esto

Dentro de la propia Container App hay un segundo secreto que no es "de negocio" sino de infraestructura: la contraseña de administrador del registro de contenedores (sección 6.3). Se maneja igual, como un secret de la Container App, nunca como texto plano en una variable de entorno visible.

secrets: [
  { name: 'doc-intel-key', value: azureDocumentIntelligenceKey }
  { name: 'acr-password', value: acr.listCredentials().passwords[0].value }
]
// las variables de entorno los referencian por nombre, no por valor:
env: [
  { name: 'AZURE_DOCUMENT_INTELLIGENCE_KEY', secretRef: 'doc-intel-key' }
]
Idea clave

@secure() protege el parámetro durante el despliegue (no queda en logs de Azure). Que el archivo con el valor real nunca se suba a Git es una regla distinta, aplicada con .gitignore. Hacen falta las dos: una sin la otra deja un hueco.

Autoevaluación
  1. ¿@secure() impide que el valor quede escrito en un archivo del repositorio?
    No. Solo evita que Azure lo registre en sus propios logs de despliegue. Que no quede en el repo depende de mantener el archivo de parámetros reales fuera de Git.

SECCIÓN 6Tres errores reales (y cómo se diagnosticaron)

El primer intento de desplegar main.bicep en una cuenta de "Azure for Students" no funcionó a la primera. Tres errores aparecieron, en orden, cada uno tapando al siguiente. Verlos en orden es más útil que verlos resueltos: cada uno enseña una forma distinta de leer un mensaje de error de Azure.

#Código de errorCausa realCómo se arregló
1RequestDisallowedByAzureLa suscripción tiene una Azure Policy de restricción de regiones que solo permite desplegar en belgiumcentral, chilecentral, westus2, brazilsouth y canadacentral — y el despliegue pedía eastus2.Cambiar el parámetro location por defecto a westus2, tras confirmar la lista exacta con az policy assignment list.
2InvalidResourceGroupLocationEl resource group rg-ms-tercero ya existía, creado a mano en un intento anterior (antes de pasar a IaC), y había quedado fijado en eastus2. Un resource group no puede "moverse" de región una vez creado.Confirmar que estaba vacío (az resource list), borrarlo (az group delete) y esperar a que desapareciera (az group exists en bucle) antes de reintentar.
3ExpressEnvironmentFeatureNotSupportedLas cuentas de estudiante crean, por defecto, un entorno de Container Apps de nivel "Express", que no soporta autenticar el pull de imágenes con identidad administrada (sección 4).Activar adminUserEnabled: true en el ACR y autenticar la Container App con usuario/clave de administrador (acr.listCredentials()) en vez de con la identidad del sistema.
Trampa

El error 2 no lo causó el Bicep: lo causó un residuo de un intento manual anterior a adoptar IaC. Es la trampa clásica de mezclar infraestructura creada a mano con infraestructura declarada en código: el código asume que parte desde cero, y el resource group ya no estaba vacío conceptualmente (tenía una región "congelada").

Ejemplo real

El comando que reveló la causa del error 1 fue az policy assignment list, que mostró una asignación de la definición sys.regionrestriction con la lista exacta de regiones permitidas. Sin ese comando, el error RequestDisallowedByAzure por sí solo no dice cuáles regiones sí están permitidas — solo que la elegida no lo está.

Ojo con esto

El nivel "Express" de Container Apps Environment no es una limitación de Bicep ni de ms-tercero: es una limitación de las suscripciones gratuitas o de estudiante. En una suscripción de pago, con un entorno "estándar" (Workload Profiles), el pull por identidad administrada sí funciona, y el ACR podría quedar sin usuario de administrador habilitado (más seguro).

Autoevaluación
  1. ¿Por qué el error 2 (InvalidResourceGroupLocation) no se podía arreglar solo editando el Bicep?
    Porque el recurso ya existía con una región fija desde antes; había que borrarlo primero y dejar que el despliegue lo volviera a crear en la región correcta.
  2. ¿Qué pregunta responde az policy assignment list que el mensaje de error por sí solo no responde?
    Cuáles son las regiones concretas que SÍ están permitidas, no solo que la elegida no lo está.

SECCIÓN 7Qué es CI/CD y por qué GitHub Actions

CI/CD son dos ideas relacionadas: Integración Continua (compilar y probar el código automáticamente cada vez que alguien sube un cambio) y Entrega/Despliegue Continuo (llevar ese cambio, ya construido, hasta donde corre en producción). Antes de este tema, desplegar un cambio en ms-tercero significaba compilar el jar a mano, construir la imagen Docker a mano, subirla al registro a mano y actualizar la Container App a mano: cuatro pasos manuales, cada uno con su propia oportunidad de olvido.

Analogía

Es la diferencia entre revisar tú mismo cada factura antes de pagarla, y tener un sistema que las revisa automáticamente apenas llegan. El trabajo (compilar, construir la imagen, desplegar) es siempre el mismo; lo que cambia es quién lo dispara y cuándo.

GitHub Actions es el motor de automatización integrado en GitHub: un archivo YAML dentro de .github/workflows/ describe una serie de pasos (un workflow) que se ejecutan en una máquina temporal de GitHub cada vez que ocurre un evento — en este caso, cada push a la rama main.

Idea clave

El pipeline de ms-tercero no reemplaza al Bicep de las secciones 1 a 6: los resuelve problemas distintos. Bicep responde "¿qué infraestructura existe?" (se ejecuta rara vez, cuando cambia la forma de la infraestructura). GitHub Actions responde "¿qué versión del código corre ahí?" (se ejecuta en cada cambio de código, mucho más a menudo).

Autoevaluación
  1. ¿Qué parte resuelve Bicep y qué parte resuelve GitHub Actions en este proyecto?
    Bicep crea y describe la infraestructura (qué recursos existen); GitHub Actions construye y despliega el código (qué versión corre dentro de esa infraestructura ya existente).

SECCIÓN 8OIDC y credenciales federadas

Para que GitHub Actions pueda ejecutar comandos az contra una cuenta de Azure, necesita autenticarse. La forma clásica sería crear un service principal con una contraseña (un client secret) y guardar esa contraseña como un secreto de GitHub. Funciona, pero esa contraseña vive para siempre hasta que alguien la rota a mano, y si se filtra, da acceso completo hasta que alguien se dé cuenta.

La alternativa usada en ms-tercero es OIDC (OpenID Connect) con una credencial federada: GitHub, en el momento exacto de ejecutar el workflow, le pide a Azure un token de identidad de corta duración y Azure lo acepta sin que exista ninguna contraseña almacenada en ningún lado. Azure confía en ese token porque, de antemano, se le dijo explícitamente de qué repositorio y de qué rama debía aceptarlo.

Analogía

Una contraseña guardada es como darle a alguien una llave física que puede copiar, perder o que alguien le puede robar. Una credencial federada es más parecido a un portero que reconoce la cara de la persona cada vez que llega: no hay ninguna llave que robar, el "acceso" se verifica en el momento, cada vez, y solo para quien coincide con la descripción exacta que se dejó por escrito.

Montar esto llevó cuatro pasos, todos ejecutados con az cli (el detalle completo de cada comando está en el apéndice A):

  1. App Registration: crear una identidad en Microsoft Entra ID que representa "el pipeline de GitHub Actions de este proyecto" (az ad app create). Devuelve un appId — el <APP_ID> de este tema.
  2. Service Principal: la "versión usable" de esa identidad dentro de esta suscripción en concreto (az ad sp create). Una App Registration puede tener un service principal por cada suscripción donde se use.
  3. Credencial federada: la regla de confianza explícita. Le dice a Azure exactamente qué debe venir en el token de GitHub para aceptarlo (az ad app federated-credential create): qué issuer (quién firma el token), qué subject (de qué repositorio y rama) y qué audience.
  4. Role assignment (RBAC): darle permisos a esa identidad sobre el resource group rg-ms-tercero (az role assignment create --role Contributor). Sin este paso, la identidad se autentica correctamente pero no puede hacer nada: autenticación y autorización son cosas distintas.
// la credencial federada de ms-tercero, con los valores reales de este proyecto
{
  "name": "github-actions-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:<tu-usuario>/<tu-repo>:ref:refs/heads/main",
  "audiences": ["api://AzureADTokenExchange"]
}
Ojo con esto

El campo subject es literal y estricto: repo:org/repo:ref:refs/heads/main solo acepta tokens que vengan de un push a la rama main de ese repositorio exacto. Un pull_request, u otra rama, u otro repositorio, generan un subject distinto y Azure rechazaría el token. Es, literalmente, el "quién puede entrar" de todo el esquema.

Idea clave

Autenticación (quién eres) y autorización (qué puedes hacer) son dos pasos separados. OIDC + credencial federada resuelve solo la primera, sin contraseña. El role assignment del paso 4 resuelve la segunda, y sigue siendo necesario exactamente igual que con cualquier otro método de autenticación.

Autoevaluación
  1. ¿Qué problema de seguridad evita OIDC frente a guardar un client secret como secreto de GitHub?
    Que no existe ninguna contraseña de larga duración que se pueda filtrar o quedar obsoleta sin rotar; el token que usa cada ejecución es de corta duración y se emite en el momento.
  2. Si la credencial federada está bien creada pero nunca se hizo el role assignment, ¿qué pasa al ejecutar el workflow?
    El login en Azure (la autenticación) funciona, pero cualquier comando que intente crear o modificar recursos falla por falta de permisos (autorización).

SECCIÓN 9El workflow de GitHub Actions, paso a paso

El archivo .github/workflows/deploy-container-apps.yml de ms-tercero tiene siete pasos. Vale la pena leerlo de arriba a abajo una vez, con calma. (La versión que ves aquí ya no es la primera que se escribió: el paso 6 original usaba az acr build en vez de Docker local — por qué cambió está en la sección 11.)

on:
  push:
    branches: [main]
  workflow_dispatch: {}

permissions:
  id-token: write   # necesario para pedir el token OIDC
  contents: read

concurrency:
  group: deploy-container-apps
  cancel-in-progress: true

on.push.branches: [main] es el disparador normal: cualquier push a main lanza el workflow. workflow_dispatch añade un botón "Run workflow" manual en la pestaña Actions de GitHub, útil para volver a desplegar sin necesidad de un commit nuevo. permissions.id-token: write es el permiso que habilita, específicamente, pedir el token OIDC de la sección 8 — sin esta línea, azure/login fallaría aunque todo lo demás esté bien configurado. concurrency evita que dos despliegues se pisen si se hacen dos push muy seguidos: el segundo cancela al primero en vez de correr en paralelo contra la misma Container App.

Autoevaluación
  1. ¿Por qué el paso de despliegue usa la etiqueta ${{ github.sha }} y no latest?
    Porque así siempre se sabe con certeza qué commit exacto está corriendo en producción; "latest" es un alias que cambia con cada build y no identifica una versión concreta.
  2. ¿Qué pasaría si se quitara la línea permissions: id-token: write?

SECCIÓN 10Secrets vs Variables en GitHub

GitHub separa la configuración de un workflow en dos cajones: Secrets (valores ocultos, que ni siquiera se pueden volver a leer una vez guardados, solo sobrescribir) y Variables (valores visibles, pensados para configuración que no es sensible). Ambos se usan en ms-tercero, y la frontera entre uno y otro es más una convención de buen criterio que una regla técnica estricta.

CajónValores de ms-terceroPor qué ahí
SecretsAZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_IDIdentifican una cuenta de Azure concreta. Con OIDC ninguno es, técnicamente, una contraseña — pero no hay razón para exponerlos en un log si no hace falta, así que se tratan con la misma disciplina que un secreto real.
VariablesAZURE_RESOURCE_GROUP, AZURE_CONTAINER_REGISTRY, CONTAINER_APP_NAMESon nombres de recursos, no credenciales. Que aparezcan en los logs de ejecución del workflow no revela nada explotable.
 
env:
  AZURE_RESOURCE_GROUP: ${{ vars.AZURE_RESOURCE_GROUP }}
  AZURE_CONTAINER_REGISTRY: ${{ vars.AZURE_CONTAINER_REGISTRY }}
  CONTAINER_APP_NAME: ${{ vars.CONTAINER_APP_NAME }}

# más abajo, en el paso de login:
- uses: azure/login@v2
  with:
    client-id: ${{ secrets.AZURE_CLIENT_ID }}
    tenant-id: ${{ secrets.AZURE_TENANT_ID }}
    subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}
Idea clave

La sintaxis ${{ secrets.X }} y ${{ vars.X }} en el YAML es lo único que cambia entre un cajón y el otro: para el workflow, ambos son simplemente texto disponible en tiempo de ejecución. La diferencia real está en que GitHub oculta el valor de un secret en la interfaz y en los logs (lo muestra como ***), y no lo hace con una variable.

Autoevaluación
  1. ¿Por qué AZURE_CLIENT_ID va como secret si con OIDC no es, técnicamente, una contraseña?
    Porque identifica de forma única la cuenta de Azure y la aplicación usada para el despliegue; aunque no sea explotable por sí solo como una contraseña, no hay ninguna necesidad de que aparezca en texto plano en los logs.

SECCIÓN 12El subject que cambia solo: IDs inmutables en el token de GitHub

El error 2 de la sección anterior merece su propio espacio porque la causa es poco intuitiva. La credencial federada (sección 8) se configuró con repo:usuario/repo:ref:refs/heads/main — el formato que la documentación de GitHub muestra como ejemplo estándar. Y aun así, Azure dijo que no coincidía con nada.

El propio mensaje de error de Azure incluye el subject real que GitHub envió, y no era el esperado:

// esperado:
repo:usuario/repo:ref:refs/heads/main

// lo que realmente llegó:
repo:usuario@33511988/repo@1432830707:ref:refs/heads/main

GitHub agrega, junto al nombre, el ID inmutable (un número que nunca cambia) tanto de la cuenta como del repositorio, en formato login@id. Es una protección de seguridad: si alguien pudiera renombrar su propia cuenta u otro repositorio para que coincida por nombre con uno legítimo, podría fabricar tokens válidos para ese nombre. Incluir el ID inmutable hace que ese ataque no funcione, porque el ID no cambia aunque el nombre sí.

Analogía

Es la diferencia entre identificar a alguien por su apodo (que cualquiera podría empezar a usar) y por su número de cédula (que es suyo, sin importar cómo lo llamen). GitHub dejó de confiar solo en el "apodo" (nombre de usuario/repo) y empezó a exigir también el "número de cédula" (el ID).

Ejemplo real

El arreglo fue literal: copiar el subject exacto del mensaje de error de Azure y actualizar la credencial federada con az ad app federated-credential update, usando ese valor tal cual en vez de intentar adivinar o reconstruir el formato login@id a mano.

Ojo con esto

No todos los repositorios muestran este formato — depende de condiciones del lado de GitHub (como si el repositorio o la cuenta cambiaron de nombre en algún momento). Si tu credencial federada con el formato simple repo:usuario/repo:... deja de funcionar de un día para otro sin que tú hayas tocado nada, este es el primer sospechoso.

Autoevaluación
  1. ¿Qué problema de seguridad previene que GitHub incluya el ID inmutable en el subject?
    Que alguien renombre una cuenta o repositorio para que coincida por nombre con uno legítimo y así obtenga tokens válidos para ese nombre; el ID no se puede falsificar ni reutilizar de esa forma.

SECCIÓN 14La salida: una región fuera del rollout de Express

Si Express es un nivel que Azure activa automáticamente para ciertas cuentas, y no hay un interruptor documentado para desactivarlo a mano, la pregunta cambia: ¿hay alguna combinación de condiciones donde Azure no pueda activarlo?

La respuesta estaba cruzando dos listas que ya existían, por separado, en este proyecto:

  • Las 5 regiones permitidas por la política de la suscripción (sección 6): belgiumcentral, chilecentral, westus2, brazilsouth, canadacentral.
  • Las regiones donde Express existe, publicadas en su documentación oficial — una lista larga, pero que no incluye belgiumcentral.

De las 5 regiones permitidas, belgiumcentral es la única que queda fuera del alcance de Express. Si Express no está disponible ahí, un entorno de Container Apps creado en esa región no puede terminar siendo "Express" — tiene que ser el nivel estándar.

Analogía

Es como buscar un hotel que no tenga una política molesta (por ejemplo, "no se admiten mascotas") cruzando la lista de hoteles donde puedes alojarte con la lista de hoteles que sí tienen esa política: el que queda en la primera lista y no en la segunda es la respuesta, sin tener que llamar a preguntar.

Ejemplo real

El cambio fue, literalmente, una línea: el valor por defecto de location en main.bicep pasó de westus2 a belgiumcentral. Todo lo demás del Bicep (sección 1 a 10) se mantuvo exactamente igual — la hipótesis solo necesitaba probarse con un redeploy completo.

Idea clave

Esta es la razón concreta, del mundo real, por la que IaC es idempotente y portable (sección 1): cambiar de región no significó reconstruir el proyecto desde cero, sino cambiar un parámetro y volver a ejecutar el mismo comando.

Autoevaluación
  1. ¿Cómo se identificó belgiumcentral como la región a probar, sin que existiera documentación que lo dijera directamente?
    Cruzando dos listas ya conocidas: las regiones permitidas por la política de la suscripción y las regiones donde Express está disponible; la única que aparece en la primera y no en la segunda era la candidata.

SECCIÓN 15Efectos secundarios de borrar y recrear un resource group

Migrar de región significó borrar el resource group en westus2 y volver a desplegarlo en belgiumcentral con el mismo nombre (un resource group no puede simplemente "mudarse" de región). Ese borrado trajo dos sorpresas que no eran obvias de antemano.

Trampa 1 · El permiso desaparece con el resource group

El role assignment de GitHub Actions (sección 8, paso 4) estaba scoped al resource group viejo. Al borrar el resource group, Azure borra también cualquier asignación de permisos que apuntara a él — tiene sentido (el scope ya no existe), pero significa que recrear el resource group con el mismo nombre no restaura el permiso: hay que volver a correr az role assignment create. El síntoma fue un login de GitHub Actions que de repente decía No subscriptions found for ***, sin ningún cambio aparente de ese lado.

Trampa 2 · El registro de contenedores vuelve a estar vacío

El ACR (sección 4) también se recreó desde cero — con el mismo nombre, pero sin ninguna de las imágenes que tenía antes. Un intento de desplegar una etiqueta que existía en el registro viejo falló con MANIFEST_UNKNOWN: manifest ... is not found: la etiqueta, simplemente, nunca había existido en el registro nuevo.

Idea clave

Borrar un resource group no es "pausar" la infraestructura: es destruirla por completo, incluidos los datos (imágenes del ACR) y las relaciones con recursos de fuera del resource group (el role assignment, que vive a nivel de identidad, no dentro del grupo). Recrear con el mismo nombre da una infraestructura con la misma forma, no la misma infraestructura.

La solución a la trampa 2 no fue técnica, sino de paciencia: dejar que el pipeline de CI/CD (secciones 9 y 11) construyera y subiera una imagen real al registro nuevo, en vez de intentar referenciar manualmente una etiqueta que ya no existía en ningún lado.

Autoevaluación
  1. ¿Por qué el role assignment no sobrevive a que se borre y recree el resource group con el mismo nombre?
    Porque la asignación apunta a un scope (el ID interno del resource group), no a su nombre; al borrarlo, Azure borra las asignaciones scoped a él, y el resource group nuevo tiene un ID distinto aunque el nombre coincida.
  2. ¿Por qué una etiqueta de imagen que funcionaba en westus2 dejó de existir en belgiumcentral?
    Porque el ACR es un recurso con datos propios (las imágenes); recrearlo en otra región no copia su contenido, crea un registro nuevo y vacío con el mismo nombre.

SECCIÓN 16Spring Boot en el contenedor: el nombre casi correcto que no sirve

Con el backend ya corriendo en belgiumcentral, el frontend empezó a recibir 401 Unauthorized al llamar a Azure Document Intelligence — a pesar de que la clave configurada era la correcta, verificada probándola directo contra la API con curl.

La causa estaba en cómo Spring Boot lee variables de entorno cuando no existe ningún application.yml dentro de la imagen (que es justo el caso en este contenedor: toda la configuración llega por variables de entorno del Bicep, sección 4). Spring Boot tiene un mecanismo llamado relaxed binding: convierte el nombre de una variable de entorno a una propiedad de configuración siguiendo una regla de conversión exacta — y si el nombre no sigue esa regla al pie de la letra, la propiedad simplemente queda vacía, sin ningún error ni advertencia.

Propiedad Java (campo)Variable de entorno que Spring esperaVariable que tenía el Bicep
azure.document-intelligence.api-key (campo apiKey)AZURE_DOCUMENT_INTELLIGENCE_API_KEYAZURE_DOCUMENT_INTELLIGENCE_KEY — sin API
azure.document-intelligence.models.cedula-model-id (campo cedulaModelId dentro de un objeto anidado models)AZURE_DOCUMENT_INTELLIGENCE_MODELS_CEDULA_MODEL_IDAZURE_DOCUMENT_INTELLIGENCE_CEDULA_MODEL_ID — sin MODELS
Analogía

Es como una casilla de correo con un código postal exacto: una carta a "casi" la dirección correcta no rebota con un aviso de error, simplemente nunca llega. AZURE_DOCUMENT_INTELLIGENCE_KEY no es "una forma válida, pero distinta" de nombrar la clave — para Spring Boot, sencillamente no es el nombre de ninguna propiedad conocida, así que la ignora en silencio.

Trampa

Este bug no apareció en ninguna prueba local anterior, porque en local sí existía un application.yml con una línea explícita como api-key: ${AZURE_DOCUMENT_INTELLIGENCE_KEY:} — ahí el nombre de la variable de entorno lo elige quien escribe el yml, no una convención automática. El relaxed binding solo entra en juego cuando no hay yml de por medio, que es exactamente la situación del contenedor en producción. Mismo nombre de variable, dos comportamientos distintos según el entorno.

Idea clave

La regla práctica de relaxed binding para variables de entorno: cada punto y cada guion de la propiedad (azure.document-intelligence.models.cedula-model-id) se convierte en un guion bajo, todo en mayúsculas. Si hay un nivel de anidamiento en el Java (un objeto dentro de otro, como models), ese nivel tiene que aparecer en el nombre de la variable — no es opcional ni se puede acortar.

Autoevaluación
  1. ¿Por qué AZURE_DOCUMENT_INTELLIGENCE_KEY no genera ningún error, solo una propiedad vacía?
    Porque relaxed binding busca una coincidencia exacta con alguna propiedad conocida; si no la encuentra, simplemente no asigna nada — no hay validación que avise de nombres "parecidos pero incorrectos".
  2. ¿Por qué este bug no se detectó en las pruebas locales?
    Porque localmente existía un application.yml que mapeaba explícitamente esa variable de entorno a la propiedad, con el nombre que quien escribió el yml decidió usar — el relaxed binding automático solo se activa cuando no hay yml.

SECCIÓN 17Afinar con datos reales: confianza, logs, y un diagnóstico que hubo que corregir

Con la autenticación arreglada, aparecieron dos problemas más, esta vez de calidad del reconocimiento de documentos — y uno de ellos enseña tanto el arreglo correcto como un diagnóstico que salió mal primero.

17.1 — El umbral de confianza, ajustado con un número real

Un RUT real, subido desde el frontend, fue rechazado con "el documento no corresponde". El log de la aplicación mostró la razón exacta:

WARN  AzureDocumentClassifierAdapter - Classifier confidence 0.81 below threshold 0.85 for docType 'rut', treating as UNKNOWN

El modelo clasificó correctamente el documento como RUT, con 81 % de confianza — pero el umbral configurado (min-confidence) exigía 85 %. No era un error de clasificación: era un umbral calibrado sin haber visto antes un caso real tan cerca del límite. Se bajó a 0.80, agregado como variable de entorno nueva (AZURE_DOCUMENT_INTELLIGENCE_MIN_CONFIDENCE) tanto en el Bicep como aplicado en caliente con az containerapp update --set-env-vars.

Idea clave

Un umbral de confianza no se ajusta "a ojo": se ajusta mirando el número real que produjo un caso real. 0.81 rechazado por un umbral de 0.85 es información concreta; bajarlo a 0.80 sin haber visto ese dato habría sido adivinar.

17.2 — El diagnóstico equivocado de la cédula (y por qué revertirlo fue lo correcto)

Con una cédula real, el resultado fue distinto: ambos campos comparados llegaron vacíos. No había ningún log de "confianza baja" para explicarlo, así que se agregó un log temporal en el adaptador de extracción mostrando todos los campos crudos que devuelve el modelo, con su confianza:

WARN  AzureDocumentExtractorAdapter - Extractor raw fields: tipo_contribuyente=[...], numero_identificacion=[content=1.061.731.887, confidence=0.826], primer_nombre=[content=JONATHAN JULIAN, confidence=0.78], segundo_apellido=[...], ...

A primera vista, esto parecía confirmar una hipótesis razonable: el código buscaba campos llamados cedula_numero, cedula_nombres y cedula_apellidos, que no aparecen en absoluto en esa lista — así que se cambiaron esos nombres en el código por los que sí aparecían en el log (numero_identificacion, primer_nombre, etc.) y se ajustaron los tests.

Trampa

Ese cambio estaba equivocado. Quien entrenó el modelo confirmó que el modelo de cédula real sí usa los nombres cedula_numero/cedula_nombres/cedula_apellidos — los campos vistos en el log pertenecían a otro modelo. La causa real: la configuración tenía el ID del modelo de cédula apuntando por error al mismo modelo que RUT (los dos usaban model_1), así que cualquier cédula real se procesaba con el modelo equivocado. El arreglo correcto fue apuntar AZURE_DOCUMENT_INTELLIGENCE_MODELS_CEDULA_MODEL_ID a model_2, y revertir el cambio de nombres de campo en el código a su versión original.

Idea clave

Un log muestra qué pasó, no necesariamente por qué era esperable que pasara. Los nombres de campo en el log eran reales y correctos — pero venían del modelo equivocado, no de uno con una nomenclatura distinta. Cuando el dato de una persona con conocimiento directo (quien entrenó el modelo) contradice una hipótesis basada en evidencia circunstancial, lo correcto es revisar la hipótesis, no insistir en ella. Revertir un cambio que resultó estar mal no es un paso perdido: es parte normal de diagnosticar.

Autoevaluación
  1. ¿Por qué bajar el umbral de confianza sin ver un caso real habría sido un error, aunque el resultado final (0.80) fuera el mismo?
    Porque el valor correcto depende de datos reales observados; adivinarlo sin evidencia puede acertar por casualidad una vez y fallar la siguiente, sin ninguna base para justificar el número elegido.
  2. ¿Qué distingue el primer diagnóstico (equivocado) del segundo (correcto) en el caso de la cédula?
    El primero asumió que el código tenía los nombres de campo mal, basándose solo en lo que mostraba un log; el segundo incorporó información externa y confiable (de quien entrenó el modelo) que reveló que el problema real era un ID de modelo mal configurado, no los nombres.

Ojo con esto

La extensión log-analytics de az cli no viene instalada por defecto, y la primera vez que se usa pregunta interactivamente si instalarla — lo cual falla en una terminal no interactiva. Se instala una sola vez, sin preguntas, con az extension add --name log-analytics --yes.

Autoevaluación
  1. ¿Cuándo conviene usar Log Analytics en vez de Log stream?
    Cuando hay que buscar algo en logs que ya ocurrieron (no en vivo), filtrando por texto, fecha o nivel — Log stream solo muestra lo que llega a partir del momento en que lo abres.

APÉNDICE BEl gotcha de Git Bash (MSYS_NO_PATHCONV)

El comando 6 del apéndice A falló la primera vez con un error que no tenía nada que ver con permisos ni con Azure:

ERROR: (MissingSubscription) The request did not have a subscription or
a valid tenant level resource provider.

La causa no estaba en Azure: estaba en la terminal. En Windows, cuando se usa Git Bash (el entorno MSYS2), cualquier argumento de un comando que empiece con una barra (/) se interpreta como si fuera una ruta de archivo de Unix, y Git Bash la "traduce" automáticamente a una ruta de Windows antes de pasársela al programa. El argumento --scope /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-ms-tercero empieza justo con esa barra, así que llegó a az convertido en una ruta de disco sin sentido — de ahí que Azure dijera que "no había una suscripción", literalmente no la reconocía como tal.

Trampa

El mensaje de error no menciona para nada a Git Bash, rutas, ni conversión de nada. Apunta directo a "falta la suscripción", lo que lleva a sospechar primero de permisos, de la sesión de az login, o del propio id de suscripción — cuando el argumento nunca llegó intacto al comando.

La solución es una variable de entorno que desactiva esa conversión automática, solo para el comando que la necesita:

MSYS_NO_PATHCONV=1 az role assignment create \
  --assignee <APP_ID> \
  --role Contributor \
  --scope /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-ms-tercero
Idea clave

Cualquier comando de Azure CLI (o de cualquier otra herramienta) ejecutado desde Git Bash en Windows, cuyo argumento empiece con /, es candidato a este problema — no solo az role assignment. Si un comando que debería funcionar falla con un error que no cuadra con lo que pediste, y estás en Git Bash, MSYS_NO_PATHCONV=1 es de las primeras cosas a probar antes de sospechar de la cuenta o los permisos.

Autoevaluación
  1. ¿Por qué el error MissingSubscription no apuntaba directamente a la causa real?
    Porque Azure recibió el argumento ya corrompido por la conversión de ruta de Git Bash; desde el punto de vista de Azure, simplemente no reconocía nada parecido a un id de suscripción válido, sin ninguna pista de que el problema era de la terminal.
  2. ¿Qué tienen en común los argumentos propensos a este problema en Git Bash?
    Empezar con una barra (/), como las rutas de recursos de Azure (/subscriptions/.../resourceGroups/...).

CONSULTAGlosario

Términos de este tema, en orden alfabético.

ABCD EGIL MOPR SUW

A

ACR Azure Container Registry
Registro privado de imágenes Docker en Azure. En este proyecto guarda la imagen del backend, con una etiqueta por cada commit (sección 4, 9).
ACR Tasks
Función de Azure Container Registry que construye imágenes Docker dentro de Azure (az acr build), sin necesitar Docker en la máquina que lanza el comando. No está permitida en la suscripción de este proyecto (sección 11); se reemplazó por docker build + docker push corriendo en el propio runner de GitHub Actions.
ARM template
El formato nativo (JSON) en el que Azure Resource Manager procesa cualquier despliegue declarativo. Bicep se compila a ARM; Azure nunca lee un archivo Bicep directamente (sección 2).

B

Bicep
Lenguaje declarativo de Microsoft para describir infraestructura de Azure, más legible que ARM. Se valida con az bicep build y se despliega con az deployment (sección 2).

C

CI/CD Continuous Integration / Continuous Deployment
Automatizar, respectivamente, la compilación/pruebas de cada cambio y su entrega hasta producción (sección 7).
Container App
El recurso de Azure que corre un contenedor concreto: su imagen, variables de entorno, puerto y reglas de escalado (sección 4).
Credencial federada federated credential
Regla explícita que le dice a Azure qué token de identidad externo (de GitHub Actions, en este caso) debe aceptar, y de cuál repositorio y rama exactos (sección 8).

D

Declarativo vs. imperativo
Un enfoque declarativo describe el resultado final deseado; uno imperativo lista los pasos exactos para llegar ahí. Bicep es declarativo (sección 1).

E

Express environment
El nivel por defecto (gratuito) de un Container Apps Environment, con menos opciones que el nivel "Workload Profiles"; no soporta pull de imágenes por identidad administrada (sección 6), ni revisionSuffix, y presentó un bug real con el pull de imágenes privadas incluso con credenciales correctas (secciones 13–14).

G

GitHub Actions
Motor de automatización de GitHub: ejecuta workflows definidos en .github/workflows/*.yml en respuesta a eventos del repositorio (sección 7, 9).

I

IaC Infrastructure as Code
Describir infraestructura en archivos de texto versionables y reproducibles, en vez de crearla a mano (sección 1).
Idempotencia
Propiedad de una operación que produce el mismo resultado sin importar cuántas veces se repita. Clave para poder reintentar un despliegue tras corregir un error (sección 1).
ID inmutable
Número interno que GitHub asigna a una cuenta o repositorio y que nunca cambia, aunque el nombre sí. Aparece en el subject de los tokens OIDC como login@id, como protección contra renombrar cuentas para falsificar tokens (sección 12).

L

Log Analytics
Servicio de Azure donde Container Apps envía los logs de la aplicación. Se consulta con KQL (Kusto Query Language), desde el portal o con az monitor log-analytics query (sección 18).

M

Managed identity identidad administrada
Cuenta de servicio gestionada automáticamente por Azure (sin contraseña que rotar) que un recurso puede usar para autenticarse contra otros recursos (sección 4).

O

OIDC OpenID Connect
Protocolo sobre el que se construyen las credenciales federadas: permite que un sistema externo (GitHub) obtenga un token de identidad de corta duración, verificable, sin contraseña almacenada (sección 8).

P

Parámetros, archivo de
Archivo JSON (main.parameters.json) que asigna valores concretos a los parámetros de un Bicep. La versión sin secretos (*.example.json) se versiona; la real, con la clave de Document Intelligence, no (sección 5).

R

Relaxed binding
Mecanismo de Spring Boot que convierte automáticamente una variable de entorno (ej. AZURE_DOCUMENT_INTELLIGENCE_API_KEY) en una propiedad de configuración (azure.document-intelligence.api-key), sin necesidad de un application.yml. Exige coincidencia exacta de nombre; si no coincide, la propiedad queda vacía sin ningún error (sección 16).
Resource group
Carpeta lógica que agrupa recursos de Azure relacionados, para administrarlos y borrarlos juntos. Vive dentro de una suscripción (sección 3).
Revisión revision
Una versión concreta y desplegada de una Container App (su imagen, variables de entorno y configuración en un momento dado). En modo de revisión única, cada actualización reemplaza a la anterior (sección 13).
Role assignment RBAC
Asignación de un rol (ej. Contributor) a una identidad sobre un recurso o un scope. Resuelve la autorización, por separado de la autenticación (sección 8).

S

Scope ámbito
El nivel de la jerarquía de Azure (suscripción, resource group, recurso) en el que opera un despliegue de Bicep o una asignación de permisos (sección 3).
Secreto vs. variable
En GitHub Actions, un secret se oculta en la interfaz y en los logs; una variable es texto visible pensado para configuración no sensible (sección 10).
Service principal
La identidad de una App Registration, usable dentro de una suscripción concreta para autenticarse y recibir permisos (sección 8).

U

Umbral de confianza confidence threshold
El valor mínimo (0–1) que Azure Document Intelligence debe reportar para que una clasificación o un campo extraído se acepte. Por debajo, se descarta aunque el dato extraído sea correcto (sección 17.1).

W

Workflow
Un archivo YAML dentro de .github/workflows/ que describe los pasos (jobs y steps) que GitHub Actions ejecuta en respuesta a un evento (sección 9).
