SECCIÓN 1Qué es una estructura de datos

Un computador guarda todo en memoria como una fila larga de bytes numerados. Cuando pides "guardar 20 nombres", el sistema te da un trozo de esa fila. La pregunta es: ¿en qué orden y con qué forma organizas ese trozo? Esa decisión es la estructura de datos.

Hay tres operaciones que hacen el 90 % del trabajo en cualquier programa:

  • Insertar: meter un dato nuevo.
  • Buscar: saber si un dato está, o cuál es su valor asociado.
  • Recorrer: pasar por todos, uno por uno.

Una colección no es "mejor" en abstracto: es mejor para una mezcla concreta de estas tres. ArrayList es excelente recorriendo y accediendo por posición; mala insertando en medio. HashMap es excelente buscando; no tiene noción de posición.

Idea clave

No existe "la mejor colección". Existe la mejor colección para tu patrón de uso: cuántos datos, cuántas inserciones, cuántas búsquedas y en qué orden recorres.

Un ejemplo que duele

Supón que tienes 100 000 correos y quieres saber si uno ya existe antes de añadirlo. Con una lista:

// MAL: recorre la lista entera por cada correo nuevo
List<String> correos = new ArrayList<>();
for (String c : entrantes) {
    if (correos.contains(c)) continue;   // O(n): mira todos
    correos.add(c);
}
// 100 000 correos: hasta 100 000 x 100 000 / 2 comparaciones

Con un HashSet, la misma tarea no recorre nada:

// BIEN: la búsqueda es casi instantánea y los duplicados se ignoran solos
Set<String> correos = new HashSet<>();
for (String c : entrantes) {
    correos.add(c);   // O(1) promedio
}

El resultado es el mismo. El tiempo, no. Esa diferencia es todo este tema.

Autoevaluación
  1. ¿Por qué "usar la colección más nueva" no es un buen criterio?
    Porque lo que importa es el patrón de uso (insertar, buscar, recorrer), no la antigüedad. Una clase vieja puede ser la correcta.
  2. Menciona dos operaciones que casi siempre quieres que sean rápidas.
    Buscar y acceder; también insertar al final en colecciones que crecen.

SECCIÓN 2El marco de colecciones: interfaces vs implementaciones

Java separa dos cosas que en otros lenguajes van juntas: qué puedes hacer (la interfaz) y cómo lo hace (la implementación). Tú programas contra la interfaz; eliges la implementación al construir el objeto.

List<String> nombres = new ArrayList<>();        // interfaz List, clase ArrayList
Map<String, Integer> edades = new HashMap<>();   // interfaz Map, clase HashMap
Idea clave

Declara siempre con la interfaz (List, Set, Map, Queue) y construye con la clase (ArrayList, HashSet…). Así puedes cambiar de implementación tocando una sola línea.

La jerarquía, de un vistazo

Iterable<E>
└── Collection<E>
    ├── List<E>      orden + posición + repetidos permitidos
    ├── Set<E>       sin repetidos (a lo sumo un elemento "igual")
    └── Queue<E>     orden de atención (FIFO, LIFO, prioridad)
        └── Deque<E>  doble extremo (cola y pila)

Map<K,V>   NO es un Collection. No se recorre con for-each directamente.
Ojo con esto

Map no hereda de Collection. Es una familia aparte porque guarda pares. No puedes escribir for (var x : unMap); iteras sobre unMap.keySet(), unMap.values() o unMap.entrySet().

Ejemplo real

El 95 % del código del día a día se resuelve con tres imports:

import java.util.List;
import java.util.ArrayList;
import java.util.Map;

El resto (Set, Deque, TreeMap, concurrentes) se añade según necesidad. La chuleta de imports los lista todos.

Saber más: por qué existen las interfaces aunque solo uses una implementación

Tres razones prácticas:

  • Sustitución: cambiar ArrayList por LinkedList, o HashSet por LinkedHashSet, sin tocar el resto del código.
  • Contratos: un método que recibe List<String> acepta cualquier lista; uno que recibe ArrayList<String> obliga al que llama a usar esa clase exacta.
  • Vistas y envoltorios: Collections.unmodifiableList(...) devuelve una List de solo lectura; List.of(...) devuelve una lista inmutable. Ambas encajan donde esperabas List.
Autoevaluación
  1. ¿Map es una Collection?
    No. Es una jerarquía aparte que guarda pares clave y valor.
  2. ¿En qué paquete vive ConcurrentHashMap?
    java.util.concurrent.

SECCIÓN 3Complejidad (Big-O) sin matemáticas

Big-O no mide segundos: mide cómo crece el trabajo cuando crecen los datos. Se escribe O(...) y dentro va lo que domina cuando el número de elementos n se hace grande.

Analogía

Buscar una palabra en un diccionario abriéndolo por la mitad y descartando la mitad cada vez: con 1000 páginas tardas unas 10 aperturas. Buscar en una lista sin orden hasta encontrarla: con mala suerte, 1000. La primera crece con el logaritmo de las páginas; la segunda, con el número de páginas. Eso es O(log n) contra O(n).

Ojo con esto

Big-O ignora las constantes. Un O(1) puede costar 2 nanosegundos y otro O(1) unos 200, pero ambos son constantes. Para n pequeños, una estructura O(n) con constante diminuta puede ganarle a una O(log n) más pesada. Big-O decide a partir de cierto tamaño.

Amortizado: el "promedio a la larga"

Algunas operaciones a veces cuestan mucho y casi siempre casi nada. ArrayList.add al final es O(1) amortizado: casi siempre es instantáneo, pero de vez en cuando hay que copiar todo el arreglo a uno más grande. Ese "de vez en cuando", repartido entre todas las inserciones, sigue dando O(1).

Peor caso vs caso promedio

La tabla hash es O(1) promedio. Si todos los datos caen en el mismo cubo por una función de hash terrible, degenera. Java mitiga eso (ver sección 10), pero el peor caso teórico existe.

Idea clave

Cuando veas "complejidad", pregúntate promedio o peor caso, y amortizado o por operación. Las tres respuestas pueden ser distintas para el mismo método.

Autoevaluación
  1. ¿O(1) significa "instantáneo"?
    No. Significa que el tiempo no crece con n. Puede ser rápido o no, pero constante.
  2. ¿Por qué ArrayList.add al final es O(1) amortizado y no O(n)?
    Porque la copia al crecer es ocasional y su costo se reparte entre muchísimas inserciones baratas.

SECCIÓN 4List: orden y posición

Una List es una secuencia ordenada y con posición. El elemento 0, el 1, el 2… Puede haber repetidos, y el orden en que metiste las cosas se conserva.

import java.util.List;
import java.util.ArrayList;
import java.util.LinkedList;
import java.util.Vector;                  // legado; casi nunca
import java.util.concurrent.CopyOnWriteArrayList;
Cuándo usar ArrayList

Por defecto, casi siempre. Si dudas, es un ArrayList. Gana cuando lees o recorres mucho y añades al final. El acceso por índice es instantáneo y los datos están contiguos en memoria, lo que la hace muy amigable para la caché de la CPU.

Cuándo usar LinkedList

Casi nunca como List. Solo tiene sentido si insertas y eliminas muchísimo en los extremos y casi nunca accedes por índice. En la práctica, para eso se usa ArrayDeque (sección 7); LinkedList gasta mucha más memoria por elemento.

Trampa

"LinkedList es más rápido para insertar" es cierto solo si ya estás parado en el nodo. Para insertar en la posición i primero hay que caminar hasta i, y eso es O(n). En un ArrayList, insertar en medio también es O(n) por el desplazamiento, pero con una constante mucho menor. Por eso ArrayList suele ganar incluso insertando.

Ejemplo

List<String> pendientes = new ArrayList<>();
pendientes.add("comprar pan");        // al final: O(1)
pendientes.add("regar plantas");
pendientes.add(0, "urgente");         // al inicio: O(n), desplaza todo
String primero = pendientes.get(0);     // O(1)
for (String p : pendientes) { ... }    // O(n)
Ojo con esto

Recorrer un LinkedList con un for por índice es un desastre silencioso:

// MAL: get(i) es O(n), así que el bucle entero es O(n^2)
for (int i = 0; i < lista.size(); i++) {
    String x = lista.get(i);
}
// BIEN: el for-each usa el iterador, que avanza con punteros: O(n)
for (String x : lista) { ... }

Con ArrayList ambos bucles dan O(n). Con LinkedList, el primero es O(n²). Con 100 000 elementos, esa diferencia es de unos 100 000 a 1.

Saber más: listas inmutables y de tamaño fijo
  • Arrays.asList(a, b, c) (import java.util.Arrays) crea una lista de tamaño fijo: puedes hacer set, pero add y remove lanzan UnsupportedOperationException.
  • List.of(a, b, c) (Java 9+) crea una lista inmutable: ni set ni add. Además rechaza null.
  • Collections.unmodifiableList(otra) devuelve una vista de solo lectura: si la lista original cambia, la vista también, pero no puedes escribir a través de ella.

Las tres son ideales para devolver datos desde un método sin exponer tu estado interno.

Autoevaluación
  1. Tu programa accede mucho por índice y añade al final. ¿ArrayList o LinkedList?
    ArrayList: acceso por índice O(1) y añadido al final amortizado O(1).
  2. ¿Por qué el bucle por índice sobre un LinkedList es peligroso?
    Porque get(i) recorre desde un extremo: cada acceso cuesta O(n) y el bucle entero O(n²).
  3. ¿List.of(...) permite add?
    No: es inmutable.

SECCIÓN 5Set: colecciones sin repetidos

Un Set es una colección donde cada valor aparece una sola vez. Si intentas añadir algo que ya está, el add devuelve false y no cambia nada. No tiene índices: no existe "el elemento 3".

import java.util.Set;
import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.TreeSet;
import java.util.EnumSet;
Cuándo usar cada uno
  • HashSet → por defecto. Solo quieres saber "¿ya está?" y no te importa el orden.
  • LinkedHashSet → quieres quitar duplicados conservando el orden de aparición. Es el "quitar duplicados sin perder el orden" que casi siempre buscas.
  • TreeSet → necesitas el conjunto siempre ordenado, o consultas como "el menor", "el mayor", "el siguiente a este".
  • EnumSet → si los elementos son de un enum. Es la más rápida y la que menos memoria usa; de hecho no existe mejor forma de guardar un subconjunto de un enum.

Ejemplo: quitar duplicados conservando el orden

List<String> conRepetidos = List.of("b", "a", "b", "c", "a");

Set<String> unicos = new LinkedHashSet<>(conRepetidos);
// unicos = [b, a, c]  sin repetidos y en el orden original

Set<String> ordenado = new TreeSet<>(conRepetidos);
// ordenado = [a, b, c]  alfabético
Ojo con esto

HashSet no promete ningún orden, y el orden puede cambiar cuando el conjunto crece (al redimensionar la tabla). Nunca produzcas una salida visible al usuario iterando un HashSet si el orden importa: dará resultados que "a veces" salen distintos y son imposibles de reproducir.

Autoevaluación
  1. Quieres quitar duplicados manteniendo el orden de aparición. ¿Qué usas?
    LinkedHashSet.
  2. Necesitas conocer el precio más bajo de un conjunto repetidamente. ¿HashSet o TreeSet?
    TreeSet: first() es O(log n). Con HashSet habría que recorrer todo, O(n).
  3. ¿Por qué EnumSet es tan eficiente?
    Porque representa el conjunto como bits de un vector: un enum pequeño cabe en un solo long.

Un Map guarda pares clave y valor. Das una clave y te devuelve su valor. Las claves no se repiten: si metes la misma clave otra vez, se sobrescribe el valor.

import java.util.EnumMap;

Cuándo usar cada uno
  • HashMap → por defecto. "Tengo una clave y quiero su valor". No importa el orden.
  • LinkedHashMap → quieres el orden de inserción. Con accessOrder=true y removeEldestEntry se convierte en una caché LRU en tres líneas.
  • TreeMap → necesitas las claves ordenadas o consultas de vecindad: firstKey, floorKey ("la clave menor o igual a esta"), ceilingKey, headMap, tailMap.
  • EnumMap → claves de tipo enum. Más rápida y compacta que HashMap para ese caso.
  • ConcurrentHashMap → varios hilos leen y escriben a la vez. Es el reemplazo correcto de Hashtable.

La operación que casi nadie aprovecha: computeIfAbsent

// Forma torpe: buscar, comprobar, crear, volver a meter
List<String> l = mapa.get(clave);
if (l == null) { l = new ArrayList<>(); mapa.put(clave, l); }
l.add(valor);

// Forma idiomática: una sola línea, y atómica en un mapa concurrente
mapa.computeIfAbsent(clave, k -> new ArrayList<>()).add(valor);

Recorrer un mapa

for (Map.Entry<String, Integer> e : mapa.entrySet()) {
    String k = e.getKey();
    Integer v = e.getValue();
}
mapa.forEach((k, v) -> System.out.println(k + " = " + v));
Ojo con esto

Iterar con keySet() y llamar get(k) dentro del bucle hace dos búsquedas por entrada. Usa entrySet(): obtienes clave y valor en una sola pasada.

Trampa

get devuelve null tanto si la clave no existe como si su valor es null. Si necesitas distinguirlo, usa containsKey o getOrDefault. Y cuidado: map.get(k).toString() explota con NullPointerException cuando la clave no está.

Saber más: una caché LRU en tres líneas con LinkedHashMap 
Map<String, String> cache = new LinkedHashMap<>(16, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, String> viejo) {
        return size() > 100;   // máximo 100 entradas
    }
};

El tercer argumento true activa el orden de acceso: cada get mueve la entrada al final. Cuando el mapa supera 100 entradas, expulsa la menos usada recientemente, que es la primera. Es el patrón clásico de caché, sin librerías.

Autoevaluación
  1. Necesitas "todas las claves entre A y M". ¿HashMap o TreeMap?
    TreeMap con subMap("A", "M"); el HashMap no tiene orden.
  2. ¿Cuál es el reemplazo moderno de Hashtable?
    ConcurrentHashMap.
  3. ¿Por qué entrySet() y no keySet() más get()?
    Porque evita una segunda búsqueda por cada entrada.

SECCIÓN 7Queue y Deque: colas y pilas

Una Queue modela una fila: lo que entra primero sale primero (FIFO). Un Deque (double-ended queue) permite meter y sacar por los dos extremos, así que sirve a la vez como cola y como pila (LIFO).

import java.util.Queue;
import java.util.Deque;
import java.util.ArrayDeque;
import java.util.PriorityQueue;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;
Cuándo usar cada uno
  • ArrayDeque → por defecto para colas y pilas de un hilo. Sustituye a Stack y hace el trabajo de LinkedList con menos memoria.
  • PriorityQueue → cuando no vale el orden de llegada sino la prioridad: tareas urgentes primero, ruta más corta en un grafo, los k mejores resultados.
  • BlockingQueue → comunicación productor/consumidor entre hilos, con put y take que bloquean en lugar de fallar.

Cola (FIFO) y pila (LIFO) con la misma clase

Deque<String> fila = new ArrayDeque<>();
fila.offer("A"); fila.offer("B");
fila.poll();   // "A"  FIFO

Deque<String> pila = new ArrayDeque<>();
pila.push("A"); pila.push("B");
pila.pop();    // "B"  LIFO
Ojo con esto

ArrayDeque no admite null. Y hay un detalle fino: cuando la cola está vacía, los métodos vienen en dos sabores. poll() devuelve null; remove() lanza excepción. peek() devuelve null; element() lanza excepción. Si la cola puede estar vacía, prefiere poll y peek.

Trampa

No uses java.util.Stack en código nuevo. Hereda de Vector, está sincronizada (lenta) y permite acceso por índice, lo que rompe la abstracción de pila. Usa ArrayDeque con push y pop.

Ejemplo real: "los k mejores" en cuatro líneas 
// Los 10 números más grandes de un flujo enorme
PriorityQueue<Integer> top = new PriorityQueue<>();
for (int x : flujo) {
    top.offer(x);                     // O(log k)
    if (top.size() > 10) top.poll();   // tira el menor
}

Memoria O(k) y tiempo O(n log k), en vez de guardar todo y ordenar: O(n log n) y toda la memoria.

Saber más: por qué PriorityQueue no está ordenada por dentro

Un montículo binario no mantiene la lista ordenada: solo garantiza que el menor (o mayor) está en la cima. Por eso peek es O(1) y poll es O(log n). Recorrer un PriorityQueue con un for devuelve un orden cualquiera, no ordenado. Si necesitas orden completo, ordena la lista o usa un TreeSet. Si solo necesitas "el siguiente más prioritario", el montículo es más barato.

Autoevaluación
  1. ¿Para una pila de un solo hilo, qué usas?
    ArrayDeque con push y pop.
  2. ¿PriorityQueue respeta el orden de llegada?
    No: saca siempre el de mayor prioridad según el comparador.
  3. ¿Qué prefieres si la cola puede estar vacía: poll() o remove()?
    poll(), que devuelve null en lugar de lanzar excepción.

SECCIÓN 8Por dentro: el array dinámico (ArrayList)

Un arreglo en Java tiene tamaño fijo: new int[10] reserva espacio para 10 y nunca para 11. Entonces, ¿cómo hace ArrayList para crecer sin límite? Con una idea sencilla y muy eficaz: guarda un arreglo más grande de lo necesario y, cuando se llena, crea uno nuevo y copia.

Analogía

Tienes una estantería de 10 huecos y la llenas. Cuando llega el libro 11 no agrandas la estantería: compras una de 15, pasas los 10 libros y tiras la vieja. Cada vez que se llena, compras una más grande. Si compraras "uno más" cada vez, pasarías libros todo el tiempo; comprando un 50 % más, lo haces cada vez menos.

Las tres variables que importan

// Dentro de java.util.ArrayList (JDK)
private static final int DEFAULT_CAPACITY = 10;   // capacidad inicial por defecto
transient Object[] elementData;                    // el arreglo donde viven los datos
private int size;                                  // cuántos elementos hay DE VERDAD
Idea clave

size no es lo mismo que elementData.length. size es cuántos elementos has metido; la longitud del arreglo es cuántos caben. Esa diferencia es la "capacidad", y es la razón de que casi todo sea tan rápido.

Cómo crece

Al añadir, si size == elementData.length, se llama a grow(), que calcula la nueva capacidad así:

// crecimiento al 50 %: nueva = vieja + vieja/2
int nueva = vieja + (vieja >> 1);   // ">> 1" es dividir entre 2
elementData = Arrays.copyOf(elementData, nueva);

Cada copia cuesta O(n), pero ocurre con frecuencia cada vez menor. El costo total de insertar n elementos es O(n), es decir, O(1) por elemento: eso es el amortizado.

Ejemplo real: por qué la capacidad inicial importa

Si sabes de antemano cuántos elementos vas a meter, evitas todas las copias:

// MAL: puede copiar el arreglo ~20 veces para 1 millón de elementos
List<Integer> a = new ArrayList<>();
for (int i = 0; i < 1_000_000; i++) a.add(i);

// BIEN: reserva una vez, cero copias
List<Integer> b = new ArrayList<>(1_000_000);
for (int i = 0; i < 1_000_000; i++) b.add(i);

Por qué el acceso por índice es O(1)

Porque los elementos están contiguos en memoria. La dirección del elemento i se calcula con una multiplicación: base + i x tamaño. No hay que recorrer nada. Y al estar todos juntos, la CPU los trae en bloque a su caché, así que recorrer un ArrayList es rapidísimo incluso frente a estructuras con mejor complejidad teórica en otras operaciones.

Por qué insertar en medio es O(n)

insertar "X" en la posición 2:

antes:  [A][B][C][D][E][ ][ ][ ]
paso 1: mover C, D, E una posición a la derecha    <-- esto es O(n)
después:[A][B][X][C][D][E][ ][ ]

Hay que desplazar todos los elementos a la derecha del hueco. Borrar en medio desplaza a la izquierda. Cuanto más al inicio, más caro.

Saber más: por qué ArrayList vacío no reserva 10 huecos de inmediato

En las JDK modernas, new ArrayList<>() no crea un arreglo de 10: guarda un arreglo vacío compartido y solo lo reemplaza en el primer add (creando uno de capacidad 10). Es una optimización de memoria: miles de listas vacías no gastan 10 huecos cada una. Es un ejemplo precioso de que, en ingeniería, "reservar por si acaso" casi siempre es peor que "crear cuando hace falta".

Autoevaluación
  1. ¿Qué diferencia hay entre size() y la capacidad?
    size() es cuántos elementos hay; la capacidad es cuántos caben.
  2. ¿Por qué añadir al final es O(1) amortizado?
    Porque casi nunca copia, y las copias ocasionales se reparten entre muchísimas inserciones baratas.
  3. ¿Por qué insertar al inicio es O(n)?
    Porque obliga a desplazar todos los elementos existentes una posición.

SECCIÓN 9Por dentro: la lista enlazada (LinkedList)

Una lista enlazada no guarda los datos juntos. Guarda nodos dispersos por la memoria, y cada nodo lleva, además del dato, la dirección del anterior y del siguiente. Es una cadena: para llegar al final, sigues los eslabones.

Analogía

Un arreglo es un edificio con habitaciones numeradas: para ir a la 500 caminas hasta la puerta 500 en línea recta. Una lista enlazada es una búsqueda del tesoro: cada pista te da la dirección de la siguiente. Insertar una pista nueva en medio es facilísimo (cambias dos notas), pero para llegar al punto medio tienes que seguir pista tras pista.

// Dentro de java.util.LinkedList (JDK)
private static class Node<E> {
    E item;          // el dato
    Node<E> next;     // puntero al siguiente
    Node<E> prev;     // puntero al anterior
}
Ejemplo real: el costo oculto en memoria

Cada nodo es un objeto aparte. En una máquina de 64 bits con referencias comprimidas, la cabecera del objeto y los tres campos ocupan del orden de 24 bytes… y encima va el valor guardado. Un ArrayList con 1 000 enteros usa unos 4 KB contiguos; un LinkedList con 1 000 enteros usa unos 24 KB más los objetos Integer, repartidos por toda la memoria. Menos caché, más basura para el recolector.

Idea clave

La lista enlazada brilla cuando el trabajo es en los extremos y el acceso es siempre secuencial. En cuanto aparece un índice, pierde. Por eso, en la práctica, ArrayDeque ocupa su lugar para colas y pilas: es una cola con la memoria de un arreglo.

Saber más: por qué existe LinkedList si casi nunca conviene

Por razones históricas y de API: implementa List y Deque a la vez, admite null (a diferencia de ArrayDeque) y ofrece un ListIterator que permite insertar y borrar con costo O(1) mientras avanzas. Ese es su nicho real: recorrer una vez e ir insertando o borrando sobre la marcha sin desplazar nada.

Autoevaluación
  1. ¿Cuánto cuesta addFirst? ¿Y get(500000)?
    O(1) y O(n) respectivamente.
  2. ¿Por qué gasta más memoria que un ArrayList?
    Porque cada elemento vive en su propio nodo con dos punteros adicionales, sin contigüidad.

SECCIÓN 10Por dentro: la tabla hash (HashMap y HashSet)

Aquí está el truco que hace que buscar sea O(1). La tabla hash convierte la clave en un número y usa ese número como índice de un arreglo. Si el número está bien repartido, la clave te dice directamente dónde buscar: cero recorridos.

Analogía

Un archivador con 16 cajones numerados del 0 al 15. Para archivar una carpeta "Pérez" no la buscas por orden: aplicas una regla (la inicial) y va derechito al cajón que toca. Casi siempre el cajón tiene poquísimas carpetas. Pero si la regla fuera "todo el que empiece por vocal al cajón 0", ese único cajón tendría medio archivador y volverías a buscar a mano.

El recorrido de una clave

1. hashCode()       -> un número de 32 bits, ej: "ana" -> 96 849
2. spread (mezcla)  -> h ^ (h >>> 16)     // revuelve los bits altos con los bajos
3. índice           -> hash & (n - 1)     // n = capacidad, potencia de 2
4. cubo             -> si está vacío: se guarda; si no: se compara con equals()
Ejemplo real

Como la capacidad siempre es una potencia de 2 (16, 32, 64…), la operación hash & (n - 1) es equivalente a hash % n pero muchísimo más rápida: una AND de bits en vez de una división. Detalle pequeño; milisegundos ganados en programas reales.

Colisiones: dos claves, un mismo cubo

Si dos claves caen en el mismo índice no es un error: se guardan en cadena dentro del cubo. Al buscar, se recorre la cadena comparando con equals().

cubos (capacidad 4):

0:  [ ]                        vacío
1:  [ana=25] -> [luis=31]      colisión: dos en el mismo cubo

Si un cubo se llena demasiado, buscar dentro de él sería O(k). Por eso, desde Java 8, un cubo con 8 elementos se transforma en un árbol rojo-negro y buscar dentro pasa a O(log k). Es una defensa contra hashes malos o maliciosos.

Ampliación (resize)

Cuando elementos > 0,75 x cubos, la tabla duplica su capacidad y reparte de nuevo todas las entradas entre los cubos nuevos. Eso cuesta O(n)… pero ocurre logarítmicamente pocas veces, así que el costo amortizado por inserción sigue siendo O(1).

Ejemplo real: evitar el resize con la capacidad inicial

Si vas a meter ~1 000 entradas, calcula la capacidad de una vez. HashMap acepta la capacidad deseada y la redondea hacia arriba a la siguiente potencia de 2 en el constructor.

// Para 1000 entradas: 1000 / 0,75 = 1334, la JDK redondea a 2048
Map<String, Integer> m = new HashMap<>((int) (1000 / 0.75f) + 1);

HashSet es un HashMap por dentro

No hay magia: un HashSet guarda internamente un HashMap donde cada elemento del conjunto es una clave y el valor es un objeto constante compartido. Por eso sus costos son idénticos. Y por eso el contrato de equals y hashCode (sección 12) es el mismo para ambos.

Saber más: quién decide el índice y por qué importa el hashCode

Tú aportas el hashCode(), y de su calidad depende todo. Un hashCode que devuelve siempre el mismo número (o que solo usa el primer carácter) mete todas las claves en pocos cubos: la tabla degenera en listas y vuelves a O(n) sin darte cuenta. Regla de oro: hashCode debe usar los mismos campos que equals y repartirse uniformemente. Para clases propias, Objects.hash(campo1, campo2) es un buen punto de partida.

En String, el hashCode se calcula como h = 31 * h + caracter para cada carácter: determinista y rápido. Java 7+ aplica además una randomización interna a las String usadas como claves, precisamente para que nadie pueda construir muchas cadenas que colisionen a propósito y degrade el mapa.

Autoevaluación
  1. ¿Qué pasa cuando dos claves dan el mismo índice?
    Se guardan en el mismo cubo (colisión) formando una cadena; se distinguen con equals().
  2. ¿Qué factor de carga usa HashMap por defecto?
    0,75.
  3. ¿Qué gana Java 8 al árbolizar un cubo lleno?
    Bajar la búsqueda dentro del cubo de O(k) a O(log k), protegiéndose de hashes malos.

SECCIÓN 11Por dentro: el árbol rojo-negro (TreeMap y TreeSet)

TreeMap y TreeSet mantienen todo ordenado en todo momento. No ordenan al final: conservan el orden mientras insertas y borras, y aun así cada operación cuesta O(log n). La estructura que lo consigue es un árbol binario de búsqueda autobalanceado: el árbol rojo-negro.

Primero, un árbol binario de búsqueda

Cada nodo tiene hasta dos hijos, con una regla: todo lo menor va a la izquierda, todo lo mayor a la derecha. Buscar es bajar comparando: en cada paso descartas medio árbol.

              50
            /    \
          30      70
         /  \    /  \
        20   40  60   80

Buscar 40:  40 < 50 -> izquierda
            40 > 30 -> derecha -> 40  OK

Eso ya da O(log n) si el árbol está equilibrado. Y ahí está el problema: si insertas datos ya ordenados (10, 20, 30, 40, 50…), todos caen a la derecha y el árbol se convierte en una línea:

10
  \
   20
     \
      30
        \
         40       // parece una lista enlazada: búsqueda O(n)
Idea clave

Un árbol binario de búsqueda sin balanceo es tan bueno o tan malo como el orden en que lleguen los datos. Un árbol rojo-negro garantiza el equilibrio pase lo que pase: su altura nunca supera el doble del mínimo posible, así que O(log n) siempre, no "a veces".

Cómo se autobalancea

El árbol rojo-negro no mide alturas en cada operación (sería caro). En su lugar, pinta cada nodo de rojo o negro y respeta cinco reglas. Cuando una inserción las rompe, hace dos cosas mecánicas y locales:

  • Rotaciones: reordenaciones de pocos nodos que bajan la altura sin cambiar el orden.
  • Recoloreo: cambiar rojos por negros para restablecer el equilibrio.

El costo se paga localmente, sobre el camino que ya recorriste, y por eso insertar sigue siendo O(log n). Las cinco reglas, en corto:

  1. Todo nodo es rojo o negro.
  2. La raíz es negra.
  3. Ningún nodo rojo tiene un hijo rojo (no hay dos rojos seguidos).
  4. Todo camino de la raíz a un hueco vacío tiene el mismo número de nodos negros.
  5. Las hojas vacías cuentan como negras.

La regla 4 es la que garantiza el equilibrio: si todos los caminos tienen los mismos negros y no hay dos rojos seguidos, el camino más largo no puede ser más del doble del más corto. Esa es toda la idea del "rojo-negro".

Ejemplo real: para qué usarlo de verdad 
NavigableMap<Integer, String> agenda = new TreeMap<>();
agenda.put(10, "Ana"); agenda.put(25, "Luis"); agenda.put(40, "Eva");

agenda.firstKey();        // 10            el menor
agenda.floorKey(30);      // 25            la clave menor o igual a 30
agenda.ceilingKey(30);    // 40            la clave mayor o igual a 30
agenda.subMap(10, 30);     // {10=Ana, 25=Luis}   un rango
agenda.descendingMap();   // al revés, sin esfuerzo

Estas consultas de "vecino" son imposibles de hacer eficientemente en un HashMap. Ahí está el valor real de TreeMap.

Ojo con esto

TreeMap y TreeSet comparan con compareTo (orden natural) o con el Comparator que les pases. Si tus claves no implementan Comparable y no das comparador, lanzarán ClassCastException. Y recuerda: usan comparación, no equals ni hashCode. Dos claves que el comparador considera iguales son la misma clave para el árbol, aunque equals diga otra cosa.

Autoevaluación
  1. ¿Por qué un árbol binario de búsqueda simple puede degenerar?
    Si los datos llegan ordenados, todos los nodos caen a un lado y el árbol se vuelve una línea, con búsqueda O(n).
  2. ¿Qué dos mecanismos usa el rojo-negro para reequilibrarse?
    Rotaciones y recoloreo.
  3. Cita dos consultas que solo un TreeMap hace fácilmente.
    floorKey y ceilingKey, firstKey y lastKey, subMap, descendingMap.

SECCIÓN 12equals() y hashCode(): el contrato que sostiene todo

Toda la eficiencia de HashSet, HashMap y LinkedHashMap depende de que tus objetos cumplan un contrato. Si lo rompes, el mapa compila, corre… y no encuentra lo que guardaste.

El contrato, en dos reglas
  1. Si a.equals(b) es true, entonces a.hashCode() == b.hashCode() obligatoriamente.
  2. Si a.hashCode() == b.hashCode(), equals puede ser true o false (una colisión es legal).

Es decir: hashCode propone el cubo, equals confirma la identidad.

Qué pasa si lo rompes

class Persona {
    String nombre;
    // sin sobrescribir equals ni hashCode
}

Map<Persona, String> m = new HashMap<>();
m.put(new Persona("ana"), "A");

String v = m.get(new Persona("ana"));
// v == null, y el mapa "crece" con claves que nadie puede encontrar

Porque sin sobrescribir, equals compara identidad (¿es el mismo objeto en memoria?) y hashCode se deriva de la dirección. Dos objetos "Ana" distintos son claves distintas. El mapa se llena de basura inalcanzable.

La forma correcta

import java.util.Objects;

class Persona {
    private final String nombre;
    private final int edad;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Persona p)) return false;   // Java 16+
        return edad == p.edad && Objects.equals(nombre, p.nombre);
    }

    @Override
    public int hashCode() {
        return Objects.hash(nombre, edad);   // mismos campos que equals
    }
}
Ojo con esto

Usa los mismos campos en equals y en hashCode. Si equals usa nombre y edad, hashCode debe usar nombre y edad. Mezclarlos es la causa número uno de mapas "que pierden cosas".

Trampa: claves mutables

Si usas como clave un objeto cuyo hashCode cambia después, la entrada queda en un cubo que ya no le corresponde: get la buscará en otro sitio y no la encontrará. Por eso las claves deben ser inmutables (String, Integer, enum, o una clase con campos final). Nunca uses una List ni un objeto que vas a modificar como clave de un HashMap.

Ejemplo real

Con record Persona(String nombre, int edad) {} la JDK genera automáticamente equals, hashCode y toString coherentes entre sí. Es la forma recomendada de crear claves hoy: te ahorras las dos sobrescrituras y los errores que conllevan.

Autoevaluación
  1. ¿Puede equals devolver true con hashCode distintos?
    No. Es exactamente lo que prohíbe el contrato.
  2. ¿Por qué una clave que muta es peligrosa?
    Porque su cubo cambia, y las búsquedas miran en el cubo del hash actual, que ya no es donde quedó guardada.
  3. ¿Qué genera un record por ti?
    equals, hashCode y toString coherentes, entre otros.

13Cómo elegir una colección (árbol de decisión)

Ya conoces las piezas. Ahora la pregunta práctica: tengo un problema delante, ¿qué colección uso? La respuesta se obtiene haciendo tres preguntas en orden.

Pregunta 1: ¿qué representa cada elemento?

  • Si cada elemento es independiente y solo importa qué hay dentro → piensas en List o Set.
  • Si cada elemento es un par clave → valor → piensas en Map.
  • Si el orden de salida importa más que el orden de guardado (colas, pilas, prioridades) → piensas en Queue / Deque.

Pregunta 2: ¿importa el orden?

Aquí está la decisión que más se equivoca la gente. "Orden" significa tres cosas distintas:

  • Orden de inserción: si meto A, B, C, quiero verlos A, B, C. → ArrayList, LinkedHashSet, LinkedHashMap.
  • Orden natural / comparación: quiero los elementos ordenados por su valor (alfabético, numérico, por Comparable). → TreeSet, TreeMap, PriorityQueue.
  • Sin orden (me da igual): la opción más rápida. → HashSet, HashMap.
Ojo con esto

HashMap y HashSet no prometen ningún orden. Que hoy te salgan "en orden" en tu máquina es casualidad de los hashes, no una garantía. Si escribes código que depende de ese orden, se romperá en otro equipo o al añadir un elemento. Si necesitas un orden, pídelo explícitamente.

Pregunta 3: ¿necesito unicidad o admito repetidos?

  • Repetidos permitidos → List o Queue.
  • Sin repetidos → Set (o las claves de un Map, que por definición son únicas).

// ¿Prohíbe repetidos?      -> Set   (HashSet / TreeSet / LinkedHashSet)
// Lo demás (orden, posición, duplicados) -> List / Queue  (ArrayList / ArrayDeque)
La analogía del almacén

Un ArrayList es un pasillo de estanterías numeradas: puedes ir directo a la número 7. Un HashMap es un guardarropa con un cartelito por abrigo: buscas por nombre. Un TreeMap es el mismo guardarropa pero con los cartelitos ordenados alfabéticamente: encuentras rápido y además puedes pedir "todos los de la letra M a la P". Un HashSet es una caja sin orden: solo me importa si ya está o no.

Autoevaluación
  1. Quiero evitar correos repetidos en una lista de suscriptores y mostrarlos en el orden en que llegaron. ¿Qué colección?
    LinkedHashSet: sin duplicados y con orden de inserción.
  2. Necesito, dado un código de vuelo, saber su estado. ¿Qué colección?
    HashMap (clave String → valor estado). Si necesito recorrerlos por código ordenado, TreeMap.
  3. ¿Por qué no debo confiar en el orden de un HashSet?
    Porque no lo garantiza: depende de los hashes, que cambian con los datos y la máquina.

14Errores clásicos y cómo evitarlos

Estos son los fallos que más aparecen en código real. Casi todos tienen la misma forma: usar una colección cuyo costo real no coincide con lo que el autor imaginaba.

1. Usar List.contains() dentro de un bucle

Un contains en una List recorre todos los elementos: O(n). Si lo llamas dentro de otro bucle de n elementos, tienes O(n²). Con 100.000 elementos, eso es 10.000 millones de comparaciones.

// MAL: O(n²)
for (String x : listaA) if (listaB.contains(x)) ...;

// BIEN: O(n) -> pasamos B a un Set (que consulta en O(1))
Set<String> setB = new HashSet<>(listaB);
for (String x : listaA) if (setB.contains(x)) ...;   // ahora O(n)

2. Eliminar de una lista mientras la recorro

Casi siempre lanza ConcurrentModificationException. La solución no es copiar la lista: es usar el iterador, que sí sabe borrar con seguridad.

// MAL: excepción
for (String s : lista) if (s.isEmpty()) lista.remove(s);

// BIEN
Iterator<String> it = lista.iterator();
while (it.hasNext())
    if (it.next().isEmpty()) it.remove();

// Alternativa moderna: eliminar por predicado, en una línea
lista.removeIf(String::isEmpty);

3. Concatenar String dentro de un bucle

Cada + crea una cadena nueva (las cadenas son inmutables). Con n concatenaciones son O(n²) en memoria y tiempo.

// MAL: O(n²)
String s = "";
for (String w : palabras) s += w;

// BIEN: O(n)
StringBuilder sb = new StringBuilder();
for (String w : palabras) sb.append(w);
String s = sb.toString();

4. Olvidar el equals/hashCode

Ya lo vimos en la (sección 12), pero es el error número uno. Sin ellos, un objeto usado como clave en un HashMap nunca vuelve a encontrarse; un HashSet acepta "duplicados" que tú consideras iguales.

5. Elegir LinkedList "porque es más rápida para insertar"

Es una intuición de libro de texto que en la práctica sale mal. ArrayList gana casi siempre por localidad de caché: sus elementos viven juntos en memoria, así que el procesador los lee de golpe. Los nodos de una LinkedList están dispersos y cada salto cuesta. A menos que tengas un caso muy específico (insertar y borrar masivamente en los extremos o con un iterador ya posicionado), usa ArrayList.

6. Confiar en la capacidad por defecto cuando conoces el tamaño

Un ArrayList arranca con capacidad 10 y va duplicando y copiando. Si sabes que vas a meter 1.000.000 de elementos, pídelo desde el principio y evitas decenas de copias.

// MAL: crece y copia ~17 veces hasta llegar al millón
List<Integer> l = new ArrayList<>();

// BIEN: reserva desde el inicio
List<Integer> l = new ArrayList<>(1_000_000);

7. Modificar una colección desde varios hilos sin protección

Un HashMap tocado por dos hilos a la vez no "da un resultado raro": en versiones antiguas podía entrar en un bucle infinito y colgar la CPU. Las colecciones de java.util no son seguras para hilos. En la (sección 15) ves la solución.

Resumen de la trampa

Casi todos estos errores son la misma historia: un método O(n) escondido dentro de un bucle. Antes de escribir un bucle, pregúntate qué complejidad tiene cada cosa que haces dentro de él. Ahí es donde explotan los programas lentos.

Autoevaluación
  1. ¿Qué lanza ConcurrentModificationException y por qué?
    Modificar una colección mientras se recorre con for-each, porque el iterador detecta que el "contador de versiones" cambió.
  2. ¿Por qué ArrayList suele ganarle a LinkedList en la práctica?
    Por localidad de caché: accede a memoria contigua y el procesador la trae en bloque.
  3. Pasar B a un HashSet antes de comparar con A, ¿en qué cambia la complejidad?
    De O(n²) a O(n): cada consulta pasa de recorrer la lista a calcular un hash.

15Java moderno y concurrencia

Interfaces var y colecciones inmutables

Desde Java 9, List.of(), Set.of() y Map.of() crean colecciones inmutables (no se pueden modificar) con una sola línea:

List<String> dias = List.of("lun", "mar", "mie");
Map<String, Integer> edad = Map.of("ana", 30, "luis", 25);

dias.add("jue");   // UnsupportedOperationException

Son la opción correcta cuando la colección es un dato fijo: constantes, catálogos, resultados de configuración. Además son ligeras y, al no poder cambiar, puedes compartirlas entre hilos sin miedo.

La interfaz var y el tipado al frente

Al declarar, se prefiere la interfaz, no la implementación, porque deja libre el cambio de implementación:

List<String> nombres = new ArrayList<>();   // declaro List, uso ArrayList

Si mañana quieres LinkedList, cambias una sola palabra. Si declararas ArrayList<String> nombres, el resto del código quedaría atado a esa clase.

Vista y envoltorios: Collections

La clase Collections (¡ojo, con s; la interfaz es Collection sin s!) tiene métodos de utilidad estáticos:

Collections.sort(lista);                       // ordena en su lugar
Collections.unmodifiableList(lista);            // vista de solo lectura
Collections.synchronizedList(lista);           // envuelve con candado (legado)

Concurrencia: cuando hay varios hilos

Las colecciones de java.util no son seguras para hilos. Para usarlas desde varios hilos a la vez, Java ofrece el paquete java.util.concurrent:

Ojo con esto

Hashtable (con t minúscula, clase antigua) y Vector no se usan hoy. Bloquean toda la colección en cada operación. Se reemplazan por HashMap y ArrayList, o por las versiones de java.util.concurrent cuando hay hilos.

Dato real

ConcurrentHashMap no bloquea todo el mapa: divide el trabajo en segmentos y solo bloquea la parte afectada. Eso permite que muchos hilos lean y escriban a la vez sin pisarse, algo que Hashtable no logra.

Streams: la colección como origen de datos

Los streams (Java 8, en java.util.stream) no son una colección: son una tubería de operaciones sobre una colección. Se describe qué quieres, no cómo recorrerlo.

List<String> largos = personas.stream()
        .filter(p -> p.edad() >= 18)
        .map(Persona::nombre)
        .sorted()
        .collect(Collectors.toList());

Úsalos para transformar y filtrar, no para acumular dentro de un bucle. Si lo que necesitas es sumar un acumulador complicado con efectos secundarios, un bucle normal suele ser más claro.

Lo esencial de esta sección

Colecciones inmutables para datos fijos (List.of). Declara siempre por la interfaz. Y en cuanto haya hilos, cambia java.util por java.util.concurrent: no es opcional.

Autoevaluación
  1. ¿Qué diferencia hay entre Collection y Collections?
    Collection es la interfaz raíz; Collections es una clase con métodos de utilidad estáticos.
  2. ¿Por qué List.of(...) es preferible a crear una lista y no modificarla?
    Porque la inmutabilidad queda garantizada por el tipo: nadie puede alterarla, ni por descuido.
  3. ¿Qué colección uso si dos hilos escriben en un contador de frecuencia por clave?
    ConcurrentHashMap (o HashMap + AtomicInteger, según el caso).

CONSULTAGlosario A–Z

Todos los términos del tema, en orden alfabético. Escribe para filtrar.

ABCD EFHI LOPR STV

A

Amortizado amortized
Costo promedio de una operación a lo largo de muchas llamadas, repartiendo los picos caros. Insertar al final en un ArrayList es O(1) amortizado: casi siempre instantáneo, salvo cuando toca copiar el array (sección 8).
Árbol binario de búsqueda BST
Árbol en el que cada nodo tiene izquierda (menores) y derecha (mayores). Buscar cuesta O(log n) si está equilibrado, y O(n) si degenera en una "línea". Por eso existen los árboles auto-equilibrados (sección 11).
Árbol rojo-negro red-black tree
Árbol binario de búsqueda que se mantiene equilibrado con dos colores y cinco reglas. Es lo que usa TreeMap/TreeSet por dentro (sección 11).

B

Big-O
Notación que describe cómo crece el costo de un algoritmo cuando crece la entrada. O(1) constante, O(log n) logarítmico, O(n) lineal, O(n log n), O(n²) cuadrático (sección 3).

C

Capacidad capacity
Cuántos elementos caben actualmente en una estructura "sin crecer". La capacidad no es lo mismo que el tamaño (size): un ArrayList puede tener capacidad 16 y tamaño 3 (sección 8).
Colección collection
Objeto que agrupa varios elementos. En Java, Collection es la interfaz raíz de List, Set y Queue; Map queda aparte porque guarda pares (sección 2).
Colisión collision
Ocurre cuando dos claves distintas producen el mismo índice en una tabla hash. No es un error: se resuelve guardándolas juntas en el mismo cubo (sección 10).
Comparable
Interfaz que le da a una clase su orden natural: define compareTo. Es lo que permite meter objetos en un TreeSet o PriorityQueue (sección 13).
Comparator
Regla de orden externa a la clase. Sirve para ordenar lo mismo de varias formas distintas sin tocar la clase (sección 5).
Cubo bucket
Cada "cajón" de una tabla hash, identificado por un índice. Las claves que caen en el mismo cubo se guardan en una lista (o árbol) dentro de él (sección 10).

D

Deque double-ended queue
Cola de doble extremo: se puede insertar y sacar por ambos lados. Sirve como cola (FIFO) y como pila (LIFO). La implementación recomendada es ArrayDeque (sección 7).

E

equals()
Método que decide si dos objetos son iguales en contenido. Por defecto compara identidad (misma dirección). Si lo sobrescribes, hay que sobrescribir hashCode de forma coherente (sección 12).

F

Factor de carga load factor
Proporción de ocupación a partir de la cual una tabla hash se agranda. En HashMap es 0,75: cuando el 75 % de los cubos tiene algo, la tabla duplica su capacidad (sección 10).
FIFO
First In, First Out: el primero que entra es el primero que sale. Es el comportamiento de una cola (sección 7).

H

hashCode()
Número entero que resume un objeto, para repartirlo entre los cubos de una tabla hash. Dos objetos iguales deben tener el mismo hashCode; dos distintos pueden compartirlo (sección 12).
HashMap
Diccionario sobre tabla hash, sin orden garantizado. La opción por defecto para clave→valor (sección 6, sección 10).
Heap (montículo) heap
Zona de memoria donde viven los objetos (a diferencia de la pila, stack, que guarda variables locales y llamadas). No confundir con la clase PriorityQueue, que implementa un montículo binario (sección 7).
Homogénea (colección)
Colección donde todos los elementos son del mismo tipo. Los genéricos <T> de Java lo garantizan en tiempo de compilación (sección 2).

I

import
Instrucción que trae al archivo una clase de otro paquete. Las colecciones viven casi todas en java.util (apéndice B).
Inmutable (colección)
Colección que no se puede modificar tras crearla, como las de List.of(). Son seguras de compartir y evitan cambios accidentales (sección 15).
Iterador iterator
Objeto que recorre una colección elemento a elemento y permite borrar con seguridad durante el recorrido (sección 14).

L

LIFO
Last In, First Out: el último que entra es el primero que sale. Es el comportamiento de una pila (sección 7).
Lista enlazada linked list
Estructura donde cada elemento es un nodo que guarda su valor y un puntero al siguiente. Insertar es barato; llegar al elemento i exige recorrer (sección 9).
Localidad de caché cache locality
Ventaja de tener los datos contiguos en memoria: el procesador los trae en bloque y los recorre mucho más rápido. Es la razón por la que ArrayList suele ganar a LinkedList (sección 9, sección 14).

O

O(1)
Costo constante: da igual que haya 10 o 10 millones de elementos, tarda lo mismo (sección 3).
O(log n)
Costo logarítmico: cada paso descarta la mitad del problema. Duplicar los elementos añade un solo paso. Es lo que cuesta buscar en un árbol equilibrado (sección 3, sección 11).
O(n)
Costo lineal: crece en proporción a los elementos. Recorrer una lista es O(n) (sección 3).
O(n log n)
Costo del mejor ordenamiento por comparación (mergesort, timsort). Es el suelo de "ordenar" (sección 3).
O(n²)
Costo cuadrático: el clásico "bucle dentro de bucle". Con 10.000 elementos son 100 millones de pasos. Es el síntoma de un método O(n) escondido dentro de un bucle (sección 14).

P

Pila stack
Estructura LIFO. En Java moderno se implementa con ArrayDeque (push/pop); la clase Stack es legada (sección 7).
PriorityQueue
Cola en la que el primero en salir no es el más antiguo, sino el de mayor prioridad (menor valor, por defecto). Se implementa con un montículo binario (sección 7).

R

record
Clase concisa de Java 16+ que genera automáticamente equals, hashCode y toString. Ideal para claves inmutables (sección 12).
Rehash
Recalcular la posición de todas las claves cuando una tabla hash se agranda, porque el índice depende de la capacidad (sección 10).
Rotación rotation
Operación local de un árbol que cambia la forma sin romper el orden, para reequilibrarlo. Es la pieza que mantiene un rojo-negro en O(log n) (sección 11).

S

Set
Colección sin elementos repetidos. Decide "repetido" usando equals y hashCode (sección 5).
Stream
Tubería de operaciones (filtrar, transformar, agrupar) sobre una colección. No es una estructura de datos: es una forma de recorrerla (sección 15).

T

Tabla hash hash table
Estructura que calcula la posición de un elemento a partir de su clave, logrando búsquedas O(1) en promedio. Es el motor de HashMap y HashSet (sección 10).
Tamaño size
Cuántos elementos hay actualmente guardados. Distinto de la capacidad (sección 8).
Treeify treeify
Conversión automática de un cubo de tabla hash en un árbol, cuando acumula demasiadas colisiones (umbral 8 en la JDK). Evita que el peor caso sea O(n) (sección 10).
Type erasure
Mecanismo por el que Java borra los genéricos <T> al compilar: existen para el compilador, no en tiempo de ejecución. Por eso no puedes crear new T[] (sección 2).

V

Vista view
Objeto que refleja otra colección sin copiarla. keySet() o subList() son vistas: cambiarlas cambia el original (sección 6).
